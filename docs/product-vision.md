# Homefit Product Vision

> 이 문서는 `docs/design/*`보다 **상위 수준의 제품 원칙**이다. 개별 설계·구현은
> 이 문서와 충돌하면 이 문서를 우선한다. 새 기능은 §12 체크리스트를 통과해야 한다.

---

## 0. North Star

> **우리 가족에게 맞는 집이 아니라, 우리 가족에게 맞는 *주거 선택*을 찾는다.**
> *Find the right housing decision for us — not just the right apartment.*

대안 표현(맥락별로 사용 가능):
- "집을 고르는 게 아니라, 어떻게 들어갈지를 고른다."
- "정보가 아니라 결정을 돕는다."

핵심은 **명사(집)가 아니라 동사(결정)**다. Homefit의 성공은 매물을 많이 보여주는
것이 아니라, 사용자가 **근거 있는 주거 결정을 내리게** 하는 것이다.

---

## 1. 핵심 문제

기존 부동산 서비스가 강한 질문:
- 이 아파트 실거래가는? 얼마나 올랐나? 주변 시세는? 학군/교통은? 어떤 매물이 있나?

**Homefit이 답하려는 질문:**
> **"우리 가족의 조건에서는 *어디에*, *어떤 방식으로* 들어가는 것이 가장 적합한가?"**

즉 Homefit은 *Property Information Service*가 아니라 **Housing Decision Support
Service**다. 데이터 조회가 목적이 아니라, **개인화된 의사결정 레이어**가 목적이다.

---

## 2. 핵심 사용자 입력 (Household Context)

Homefit은 지역/가격 검색 이전에 **가구 맥락**을 먼저 이해한다.

- 거래 목적(매매/전세) · 가용 현금 · 최대 예산 · 소득/파이낸싱 프로파일
- 두 사람의 직장 위치 · 각자의 통근 방식·허용시간
- 희망 평형 · 자녀 계획 · 입주 희망 시점
- 중요하게 여기는 요소(우선순위) · 절대 포기 불가 조건(dealbreaker)
- 향후 청약/주택구입 계획

**레이어링 원칙**: 민감/정책 판정용 정보는 기본 온보딩에 전부 넣지 않는다.
- 기본 온보딩 = 후보를 좁히는 최소 조건(`UserConditions`).
- 필요 시 확장 = `HouseholdProfile`(청약·대출 자격), 향후 `FinancingProfile`.
- 참조: `docs/design/onboarding.md`, `data-phase2c-household-eligibility.md`.

---

## 3. Homefit이 비교하는 것 = 주거 전략(Acquisition Path)

Homefit은 '아파트끼리'만 비교하지 않는다. **주거로 들어가는 방식 자체**를 비교한다.

```
기존주택 매매  vs  전세 거주  vs  청약  vs  분양권 매수  vs  개발 예정지 대기
```

그래서 핵심 질문은
> "A아파트 vs B아파트, 어디가 좋은가?"
에서 끝나지 않고
> "지금 A를 매수할까 / B에 전세로 살며 청약을 기다릴까 / C에 청약할까 /
> 합법적으로 거래 가능한 D분양권을 매수할까?"
까지 확장된다.

이 구조는 이미 도메인에 반영돼 있다: **`kind`(물리적 유형: existing/presale/area)**
와 **`AcquisitionPath`(취득 방법: subscription/resale/existing_trade)**를 분리
(`docs/design/presale-rights.md` §2·§3). 같은 단지가 lifecycle에 따라 취득경로가
전이한다.

---

## 4. 핵심 가치 제안 — Understand → Compare → Decide

### Understand
우리 가족의 조건·우선순위·제약을 구조화해 이해한다(§2).

### Compare
**성격이 다른 선택지를 동일한 의사결정 맥락에서** 비교한다. 기존주택·분양·분양권·
개발예정지를 각자의 척도로 평가하되, 하나의 결정 화면에서 나란히 본다(직접 점수
합산은 하지 않는다 — §5).

### Decide
점수 순위로 끝내지 않는다. 각 선택지의 **장단점·제약·비용·시간축·불확실성**을
설명해 사용자가 스스로 결정하게 한다.

**제품의 핵심 산출물은 `아파트 랭킹`이 아니라 `Housing Strategy / Decision View`다.**

## 5. Decision Model (요소를 하나의 점수로 합치지 않는다)

```
   HomeFit / AreaFit        (적합도 — 결정적, 정책 무관)
        ×
   Affordability            (감당가능성 — 현금흐름·파이낸싱)
        ×
   Subscription Eligibility (청약 자격 — 정책 버전드)
        ×
   Transfer Eligibility     (전매 가능/조건 — 근거·검증)
        ×
   Timing                   (입주·전매·청약 시점 축)
        ×
   Risk / Unknowns          (위험·미확인)
        ↓
     Decision View
```

각 요소의 역할:

| 요소 | 역할 | 원칙 |
|------|------|------|
| **HomeFit** | 지점(집)이 우리 7축 우선순위에 맞는 정도 | 결정적 계산 |
| **AreaFit** | 지역(면)이 우리 우선순위에 맞는 정도 | 결정적, **HomeFit과 직접 비교 금지** |
| **Affordability** | 지금 필요한 현금·향후 납부부담·감당가능성 | 점수 아님, 별도 레이어 |
| **Subscription Eligibility** | 청약 프로그램별 자격(신혼·생애최초·신생아 등) | 정책 버전드(출처·기준일), 점수 아님 |
| **Transfer Eligibility** | 분양권 전매 가능/조건/위험 | 근거·검증 상태, 점수 아님 |
| **Timing** | 입주·전매해제·청약 일정의 시간축 | lifecycle에서 파생 |
| **Risk / Unknowns** | 미확인 항목·데이터 신뢰도·거래 위험 | fail과 구분해 표시 |

### 절대 원칙 (설계에 이미 반영)
- **HomeFit과 AreaFit을 동일 점수처럼 직접 비교하지 않는다**(성격이 다른 척도).
- **정책 자격을 적합도 점수에 섞지 않는다**(직교 — domain-model-v2 §5).
- **거래 가능 여부를 적합도에 섞지 않는다**(presale-rights §7).
- **데이터가 없다는 이유로 0점 처리하지 않는다.** `unknown`은 `fail`과 다르다
  (DealbreakerStatus: pass/fail/unknown).
- **AI가 법적/정책적 자격이나 numeric score를 임의로 결정하지 않는다.** 점수는
  결정적 계산, 자격은 버전드 데이터, AI는 설명 역할.

## 6. Homefit이 만들지 않을 것 (Scope Guardrail)

Homefit은 다음을 **대체하려 하지 않는다**:
- 종합 부동산 매물 플랫폼(모든 매물 나열)
- 실거래가 전문 분석 서비스(시세 차트·거래량·통계 심층분석)
- 장기 시세 추세/투자분석 서비스
- 지도 기반 '모든 부동산 정보' 서비스
- 청약 공고 원문 열람 서비스
- 부동산 뉴스/커뮤니티
- **불법·편법 분양권 거래 지원**(전매제한 우회·명의변경 우회·이면/다운계약 등 —
  presale-rights §0)

외부 서비스·공공데이터가 더 잘 제공하는 정보는 **의사결정에 필요한 만큼만** 가져와
쓴다(원문 재판매·전시가 목적이 아니다).

### 기능 추가 판단 기준
> "부동산 서비스에 흔히 있는 기능인가?"가 **아니라**
> **"이 정보가 사용자의 주거 의사결정을 실제로 바꾸는가?"**

YES인 것을 우선한다. NO면, 아무리 흔한 기능이어도 넣지 않는다.

## 7. 데이터의 역할 — 목적이 아니라 Decision Engine의 input

실거래가·지도·통근시간·학교·생활인프라·청약공고·정책정보는 **그 자체가 목적이
아니다.** 전부 **결정 엔진의 입력**이다.

```
External / Public Data
  → Adapter        (공급자 raw를 domain 타입으로 변환 — 경계)
  → Repository     (조회 추상화, 공급자 교체 가능)
  → Domain         (순수 타입·불변)
  → Deterministic Decision Logic (computeHomeFit/AreaFit·자격·현금흐름)
  → Decision View
```

- **외부 API 응답이나 특정 공급자 데이터 모델이 domain/scoring/UI를 직접
  지배하지 않는다**(`docs/design/real-data-integration.md` 원칙 1).
- 지도·차트 같은 표현 계층도 "정보 전시"가 아니라 "결정을 돕는 뷰"로 존재한다.

---

## 8. 카테고리 차별화

특정 서비스 비방이나 기능표 비교가 아니라 **카테고리 자체가 다르다**:

| 카테고리 | 답하는 질문 |
|----------|-------------|
| Property Search | "어떤 집이 있는가?" |
| Property Intelligence | "이 집/지역은 어떤가?" |
| **Homefit** | **"우리에게 어떤 선택이 맞는가?"** |

Homefit은 부동산 데이터 서비스를 복제하는 게 아니라, 여러 데이터를 **사용자 조건과
결합해 personalized housing decision layer**를 만든다.

## 9. 대표 사용자 시나리오

### Scenario A — "지금 매수할까?"
**입력**: 가용현금 5억·소득·직장(강남/판교)·자녀계획 있음·34평 희망.
**Homefit**: 기존주택 매매 후보들을 HomeFit으로 랭크 + Affordability(대출 포함
감당가능성) + dealbreaker 통과 여부.
**Decision View 예시**:
> "미사 A단지 — 예산·평형 적합(HomeFit 87). 단, 2번째 직장 통근이 기준보다 12분
> 김. 지금 현금으로 감당 가능(LTV 여유). 즉시 입주 가능." vs "동탄 B — 더 저렴·
> 통근 우수하나 학군 지표 낮음."

### Scenario B — "매수 vs 전세+청약"
**입력**: 무주택·청약통장 5년·신혼 3년·신축 선호·2년 내 입주 유연.
**Homefit**: (1)지금 구축 매수 vs (2)신축지역 전세 거주하며 청약 대기, 두 **전략**을
비교. 청약 대기 전략엔 Subscription Eligibility(신혼부부 특공 가능성)·예상 청약
일정(Timing)·전세 자금 부담(Affordability)을 함께.
**Decision View 예시**:
> "① 지금 구축 매수: 즉시 안정, 신축 프리미엄 없음. ② 전세+청약: 신혼부부 특공
> **가능성 있음**(소득·자산 요건 통과, 통장 OK), 대상 단지 3건 공고 예정(2026 하반기).
> 다만 당첨 불확실(Risk), 그동안 전세 자금 필요." → 순위가 아니라 **두 갈래의
> 조건·리스크·시간축** 제시.

### Scenario C — "청약 vs 분양권"
**입력**: 청약 자격 애매(사실혼)·자금 여유 있음·특정 지역 입주 원함.
**Homefit**: 청약 예정 단지(subscription) vs 전매 가능 분양권(resale)을 **자금·
입주시점·자격·위험**까지 포함해 비교.
**Decision View 예시**:
> "청약 C단지 — 분양가 낮음, 그러나 사실혼은 신혼 특공 **대상 아님**(혼인신고
> 필요), 일반공급은 경쟁 큼. 분양권 D — 지금 매수 가능(🟢 전매 가능·공고 근거·
> 검증일 …), 필요 현금 X억(프리미엄 포함), 2028 입주. 단 잔여 중도금 부담 · 권리
> 확인 필요(Risk)." → 각 경로의 **자격·현금·시점·위험**을 나란히.

각 시나리오의 공통점: 결과가 **점수 하나가 아니라, 조건·이유·제약·리스크·다음
행동을 담은 Decision View**다.

## 10. 제품 UX 원칙

데이터 테이블을 던지고 "알아서 판단하라"고 하지 않는다. 정보 구조는:

```
조건 → 추천 → 이유 → 비교 → 제약/리스크 → 다음 행동
```

- 숫자에서 끝내지 않는다. "89점"이 아니라
  **"예산·평형엔 잘 맞지만, 2번째 직장 통근이 기준보다 12분 깁니다."**
- **왜 이 결과인지 설명 가능**해야 한다(축별 근거·데이터 출처·기준일).
- AI가 추가돼도 **AI는 결정적 결과와 검증된 데이터를 설명하는 역할이 우선**이며,
  없는 사실/점수/자격을 생성하지 않는다(§5 마지막 원칙과 동일).

## 11. Feature Decision Checklist

새 기능을 설계/구현하기 **전에** 확인한다:

1. 이 기능이 실제 주거 의사결정을 개선하는가?
2. 단순 정보 조회 기능을 복제하고 있지는 않은가?
3. 기존 외부 데이터/서비스를 활용할 수 있는가(직접 재구축 대신)?
4. 사용자 조건과 결합했을 때 **새로운 가치**가 생기는가?
5. 결과의 근거를 설명할 수 있는가?
6. `unknown`과 `fail`을 구분하는가?
7. 정책/법률 정보라면 **출처와 기준일**을 추적하는가?
8. 이 기능 때문에 Homefit이 **종합 부동산 앱** 방향으로 새고 있지는 않은가?

3개 이상 NO이거나 1·8번이 위험하면 재검토한다.

  > 제품의 정체성·범위·의사결정 원칙은 [`docs/product-vision.md`]가 단일 진실
  > 소스다. 새 기능은 그 §11 Feature Decision Checklist를 통과해야 한다.
- **Development Workflow**에 추가:
  > 설계 문서(`docs/design/*`)를 쓰기 전에 `docs/product-vision.md`와 정합하는지
  > 확인한다. 충돌 시 vision이 우선하며, vision을 바꿔야 한다면 그 변경을 먼저
  > 논의·기록한다.
- 개별 design 문서 상단에 "이 문서는 product-vision.md의 …을 구체화한다" 한 줄
  교차참조를 점진적으로 추가.
